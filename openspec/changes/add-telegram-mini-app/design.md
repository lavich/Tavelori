## Context

Мотивация описана в `proposal.md`. Текущий `src/main.tsx` запускает React с BrowserRouter, регистрирует service worker и обновляет каталог. `src/content/client.ts` устанавливает пакеты уроков и медиа по запросу. Dexie использует схему 2; полная копия переносит пользовательские таблицы, поддерживает старый формат и исключает кеш каталога. Оболочка публикуется на GitHub Pages с базовым путём `/lexi/`.

Экран занятия использует `100dvh` и системные safe-area отступы. Навигация назад реализована в компонентах приложения. Озвучка выбирает файл или системный греческий голос; сейчас отказ `audio.play()` подавляется и может быть представлен как успешное воспроизведение. Экспорт запускается через ссылку на Blob без подтверждения фактического сохранения файла. Это конкретные точки интеграции и проверки.

Существующая спецификация офлайн обещает оба исходных набора после загрузки пакета, тогда как текущая реализация загружает выбранные уроки по запросу. Дельта `local-first-app` явно согласует гарантию со скачанными уроками и отдельно описывает ограничения запуска Telegram; это изменение контракта, а не скрытое исключение.

## Goals / Non-Goals

**Goals:** единая сборка и единые упражнения для браузера и Telegram; изолированная интеграция платформы; проверяемые деградации файловых, медиа- и офлайн-возможностей.

**Non-Goals:** полная копия базы в CloudStorage, синхронизация обычного браузера с Telegram, автоматическое объединение независимых тренировок и изменение алгоритма FSRS. Создание записей произношения остаётся в отдельном изменении `complete-seed-audio-and-sources`.

## Decisions

### Единый клиент с адаптером Telegram

Добавить небольшой модуль платформы с инициализацией официального bridge, определением доступных функций и симметричной очисткой подписок. Загрузка bridge не блокирует рендер браузерного приложения; при ошибке или ограниченном ожидании остаётся обычный режим. Наличие одного глобального объекта не считать достаточным признаком запуска внутри Telegram: библиотека может присутствовать и в браузере. Параметры запуска нужны только для UI, не для доверенной идентификации.

После готовности основных элементов вызвать `ready`, при поддержке — `expand`. Не требовать полноэкранный режим и не отключать жесты глобально. Подключить официальный bridge без дополнительного React SDK: интеграция небольшая, методы можно скрыть за тестируемым интерфейсом. Альтернатива — отдельная сборка Telegram — увеличила бы риск расхождения упражнений и обновлений.

### Навигация, тема и геометрия

Telegram BackButton и внутренняя кнопка используют общий обработчик возврата, включая существующее завершение/приостановку занятия. На главном экране BackButton скрыт, без внутренней истории возврат идёт на `/`. Не полагаться исключительно на `history.length`, который может включать внешнюю историю. Подписки не должны дублироваться при React StrictMode.

Размеры и safe-area Telegram переводятся в переменные оболочки; системные и Telegram-отступы не суммируются слепо. Для экранной клавиатуры учитывать фактическую видимую область и проверить VisualViewport на устройствах. Недоступные свойства заменяются CSS-значениями браузера. Смена темы меняет семантические цвета фона, текста, границ и действий; отдельно проверить контраст статусов правильного/неправильного ответа. Собственные кнопки упражнения сохраняются вместо переноса в Telegram MainButton.

### Платформенный UI и цветовые токены

Платформенный адаптер отделён от адаптера синхронизации: он управляет возможностями back, haptic и primaryAction, подписками и очисткой; код обучения не обращается к Telegram.WebApp напрямую. Веб-реализация не вызывает вибрацию и предоставляет обычные UI-кнопки. Контракт нативного действия включает текст, loading/disabled, замену обработчика и снятие при размонтировании. Нельзя скрывать внутреннюю кнопку до подключения нативной. Существующие shadcn-компоненты и структура features сохраняются; массовое перемещение файлов не требуется.

В Telegram сопоставить существующие семантические токены Lexi с CSS-переменными Telegram: background — bg-color, card — section-bg-color с fallback на secondary-bg-color, foreground — text-color, muted-foreground — hint-color, primary — button-color, primary-foreground — button-text-color. Для каждого сопоставления определить резервный цвет. У Telegram нет универсального обязательного border-токена: границу выбирать локально с учётом темы и контраста. Цвета статусов обучения принадлежат Lexi, с подходящими для светлого/тёмного фона вариантами. Неподходящие сочетания заменяются проверенной локальной парой; цвет не является единственным сигналом результата. Не вводить состояния Again/Hard/Good/Easy, самооценку, новые вкладки или серию дней из иллюстративных рекомендаций.

Для нижнего дока исходить из viewportStableHeight, а не следовать каждому изменению viewportHeight; клавиатуру проверять с VisualViewport и реальной доступной областью. Разделять отступы устройства и перекрытия Telegram, избегая двойного отступа. Компактная шапка в Telegram убирает только повторный бренд и дублирующий back, сохраняя заголовок и доступ к «Ещё».

### Отклик ответа и эксперимент с главным действием

Запрашивать notificationOccurred после успешного локального сохранения нового ответа, не при рендере, чтении истории или синхронизации. Идентификатор события защищает от повторного отклика. Для почти правильного ответа использовать warning, для остальных — success/error; selectionChanged не используется как подтверждение ответа. Настройка по умолчанию включена только при доступном API, локальна устройству и Telegram-профилю. Пропуски, сбои записи и воспроизведения не превращаются в тактильную оценку знания; исключение API не влияет на сохранение.

Прототип сравнивает текущую кнопку «Сегодня» и Telegram MainButton вместе с нижней навигацией. Нативный вариант принимается только при доступности действия, отсутствии перекрытий/двойного CTA, корректных loading/disabled и работе «Продолжить» на iOS и Android; если любой критерий не выполнен, первый выпуск сохраняет обычную кнопку Lexi. Решение и снимки экранов фиксируются в отчёте. На упражнениях MainButton не используется. Сложные диалоги восстановления и конфликтов остаются общими компонентами Lexi; Telegram Popup и ссылки startapp на уроки в этот этап не добавляются.

### Локальная база и сохранение

Сохранить атомарность ответов и идентификаторы событий; добавить совместимую миграцию для метаданных синхронизации, очереди и отдельных профилей. Старые копии продолжают читаться; идентификаторы устройства и очередь публикации из копии не восстанавливаются. Не переносить сохранение на событие закрытия WebView: оно может не прийти. При скрытии останавливать звук, при возврате актуализировать доступность медиа и состояние экрана. Сохранённая сессия возобновляется существующим механизмом.

На первом запуске объяснить границы синхронизации. Локальные профили разделены по Telegram-пользователю и боту, браузерный профиль независим. Это выбранная архитектура: в вебе нет Telegram Login, общей серверной базы и автоматического обмена с Telegram. Пространства локальных данных различаются явно, даже когда WebView и браузер используют один origin. На экране хранения показывать «В этом браузере» либо «Telegram: облачная синхронизация». Ручной импорт копии создаёт разовый перенос, а не связь профилей. Telegram ID из контекста служит локальным селектором, не серверным доказательством личности; облачную область задаёт сам Telegram. При отсутствии контекста не открывать последний Telegram-профиль как общий. Старую локальную базу переносить в профиль только явным действием, сохранять исходник.

### Граница адаптера синхронизации

Локальные транзакции обучения и очередь изменений отделены от удалённого транспорта. Координатор синхронизации отвечает за версии, проверку снимков, конфликты и статусы; адаптер отвечает за чтение и публикацию версий, доступность транспорта и явные ограничения/ошибки. Telegram-специфические ключи, callback API и разбиение на части остаются внутри CloudStorage-адаптера. Контракт не обещает общей атомарной блокировки или compare-and-swap. Повтор публикации одной версии идемпотентен, неполная публикация не выдаётся за доступную версию.

Для веба синхронизация отключена явно: это не успешная запись в фиктивное облако. Тестовый транспорт позволяет проверить координатор без Telegram. Будущий адаптер внешней базы будет обращаться к серверному API, а не содержать пароль базы в браузере; потребуются отдельные авторизация, миграция и решение об объединении профилей. Сейчас этот адаптер не создаётся. Стабильные ID слов/ответов, версия формата и локальная очередь сохраняют возможность такого расширения.

### CloudStorage: компактные версии прогресса

Использовать официальный CloudStorage для одного пользователя одного бота. Собственный API, токен бота и cron для синхронизации не нужны. Обычный браузер не получает доступ к CloudStorage через Telegram Login: веб-синхронизация потребовала бы отдельной архитектуры с общей базой и серверной проверкой входа.

Снимок содержит состояния FSRS стандартных слов, компактные состояния навыков для выбора упражнения (включая сборку перед письмом), дневные счётчики новых слов, сводную статистику последних 7 дней, настройки и даты/статусы стандартных уроков, идентификаторы требуемых пакетов. Полные ReviewEvent и Session, личные слова/правки и Blob не передаются. Потребуется адаптировать чтение планировщика и статистики к компактной базовой сводке и последующим локальным событиям без двойного учёта; это не изменение алгоритма FSRS. Эквивалентность проверить на одинаковой последовательности ответов. Отсутствующие стандартные пакеты догружать; до загрузки не терять состояния неизвестных идентификаторов.

Каждая установка получает случайный идентификатор устройства. Версия имеет идентификатор, причинную базу (вектор счётчиков устройств), версию формата, контрольную сумму и части. Каждое устройство пишет только собственные ключи: неизменяемые части поколения и отдельный указатель на последнюю полную версию. Части укладываются в 4096 символов; указатель публикуется последним после подтверждения записи частей. Чтение проверяет все части и checksum, применяет снимок одной локальной транзакцией. Общий изменяемый указатель на весь аккаунт не используется. Записи одного устройства сериализуются между вкладками; при невозможности обеспечить одного писателя облачная запись приостанавливается.

Перед отправкой и при открытии/возврате прочитать опубликованные указатели, затем нужные версии. Если облачная версия причинно новее и локальных изменений нет — применить её. Если локальная версия продолжает известную облачную — опубликовать её. Независимые версии показывать как конфликт: пользователь выбирает целый снимок, а новая версия отмечает обе известные ветви как рассмотренные. Время используется только для отображения, не для выбора победителя. После записи повторить чтение указателей: поздняя конкурентная запись обнаруживается следующим обменом. Глобальная блокировка на setItem/getItem не считается надёжной, так как нет документированного compare-and-swap.

Конфликтующие и отвергнутые версии сохраняются до явного удаления после предложения экспорта. Устройство может удалять только собственные устаревшие поколения, которые не нужны текущим/сохранённым конфликтным версиям; временные поколения незавершённой отправки убираются после восстановления состояния. При чтении удалённого поколения повторить чтение указателя, а не применять частичные данные. Проверять вместимость до отправки с резервом на новый снимок; при превышении 1024 ключей остановить облачную запись, сохранив очередь локально. Автоматической очистки чужих ключей нет. Повтор использует тот же идентификатор версии и не удваивает прогресс.

Обмен запускается при открытии, возврате, после изменений и восстановлении сети в открытом приложении; ручной повтор доступен. Ошибки дают повтор с задержкой, не бесконечный цикл запросов. Облачный статус отделён от локального сохранения. Первое подключение непустой локальной базы к непустому облаку и восстановление копии требуют выбора состояния, а не автоматической перезаписи.

### Передача копий и аудио

Использовать текущий формат экспорта/импорта. Для сохранения копии выбирать поддерживаемый файловый share через `navigator.canShare`/`navigator.share` либо обычное скачивание; не показывать успех на основании одного открытия диалога. Обрабатывать отмену отдельно от ошибки. Нативный Telegram `downloadFile` не использовать для локального Blob: первый этап не вводит серверный URL или загрузку личной копии на сервер. Если сохранение неподдерживаемо, дать понятное состояние; не предлагать переход в браузер как способ забрать данные Telegram.

Восстановление сохраняет валидацию, staging и транзакционную замену. Если предусмотренная существующим экраном защитная копия перед заменой не может быть передана или пользователь отменяет её передачу, замену не начинать. На реальных iOS и Android хотя бы один маршрут передачи копии в обе стороны обязателен для объявления этих клиентов поддержанными. Недоступность маршрута — блокер выпуска, а не повод молча убрать требование.

Отказ воспроизведения не подавлять: предоставить повтор или пропуск аудирования без оценки знания. Файлы проверять пользовательским тестовым аудио; наличие полного аудиопакета не требуется для проверки интеграции. Не обещать системный греческий голос на каждой платформе.

### Офлайн и размещение

Сохранить разделение кеша оболочки и скачанных уроков. Регистрация service worker и запросы storage API не должны обрушать запуск, если WebView не поддерживает их. В Telegram показывать готовность данных, не гарантируя холодный запуск самого контейнера без сети. Браузерная офлайн-гарантия сохраняется.

Целевой бот — `@TaveloriBot`; ссылка запуска после настройки Main Mini App — `https://t.me/TaveloriBot?startapp`. Имя выбрано пользователем; регистрация бота и настройка в BotFather ещё не подтверждены. Main Mini App настраивается на корневой HTTPS-адрес `https://lavich.github.io/lexi/`; маршруты конкретных уроков и обработка `startapp` не входят в первый этап. Это избегает зависимости запуска от SPA fallback для вложенных URL. Бот служит точкой запуска, обработчик `/start` и webhook не требуются для этого сценария.

## Risks / Trade-offs

- [Поведение файлов и клавиатуры отличается между WebView] → эмуляция bridge в Playwright плюс обязательная проверка реальных iOS и Android с версиями клиентов.
- [Очистка локальной базы] → компактный подтверждённый прогресс восстанавливается из CloudStorage; личные медиа, полная история и неотправленные ответы требуют полной копии.
- [Внешний bridge не загрузился или клиент старый] → ограниченное ожидание, проверки возможностей, браузерный режим без блокировки базы.
- [Системный голос отсутствует или файл не проигрался] → исключение недоступного аудирования, повтор/пропуск без штрафа, остановка при скрытии.
- [Подтверждение скачивания недоступно браузерному API] → нейтральное сообщение о передаче файла, без утверждения «копия сохранена».

### Предварительная проверка на устройствах

Перед основной адаптацией экранов проверить минимальный обмен тестовым снимком, обрыв отправки и конфликт на двух реальных устройствах одного аккаунта. Здесь же проверить файловые операции, клавиатуру и звук. Результат — наблюдаемые данные, версии ОС/Telegram и список ограничений, не предположение на основании браузерных тестов. Этот прототип выполняется на этапе реализации и не заменяет финальную приёмку. При отсутствии устройств можно выполнять независимые локальные задачи, но нельзя считать интеграцию подтверждённой.

До реализации снимка составить таблицу полей и потребителей: перенос одного Card FSRS недостаточен. Проверить состояние навыка сборки/письма, дневные счётчики и сводки статистики, измерить сериализованный размер с резервом на незавершённую публикацию и конфликт. Производство полного аудиопакета не является предпосылкой прототипа: используется тестовый файл.

### Адрес приложения и возможный перенос

Для первого выпуска по умолчанию сохранить текущий HTTPS-адрес и бота. Смена хостинга не нужна для CloudStorage. При будущем изменении origin IndexedDB браузера не переносится редиректом: сначала предложить полную копию на старом адресе, затем восстановить её на новом. Сохранить старый адрес доступным на время переноса. Telegram CloudStorage того же бота может восстановить компактный прогресс, но не локальные личные медиа, полную историю или неотправленные ответы. Перед изменением URL бота сохранить их копией. Переход на другого бота — другая облачная область, а не прозрачный перенос. Порядок проверить на тестовых origin; реального переезда в этой задаче нет.

## Migration Plan

1. Добавить адаптер, профили, совместимую миграцию метаданных и проверки старых копий; не публиковать существующие данные без проверки облака.
2. Проверить сборку с `/lexi/`, обычную PWA и Telegram-режим в автоматических тестах.
3. Подготовить инструкцию BotFather для `@TaveloriBot` и ссылки `https://t.me/TaveloriBot?startapp`; токен не запрашивать в артефактах и не хранить в клиенте.
4. При выпуске настроить тестового бота, выполнить матрицу устройств: запуск двумя способами, полный урок, клавиатура, темы, BackButton, повторное открытие, потеря сети, аудио и копии в обе стороны, перенос прогресса между двумя устройствами одного аккаунта, офлайн-конфликт, изоляцию второго аккаунта. Записать версии Telegram/ОС и фактические результаты; недоступное устройство отметить как непроверенное.
5. Подключить проверенную сборку к целевому боту после прохождения матрицы. При откате убрать точку запуска Mini App или вернуть предыдущую сборку; использовать совместимую с новой локальной схемой сборку, отключить облачную запись и сохранить данные; старый клиент не должен перезаписывать неизвестный облачный формат.

### Бот разработки

Для прототипа и локальной разработки использовать созданного `@TaveloriDevBot`; ссылка после настройки Main Mini App — `https://t.me/TaveloriDevBot?startapp`. Основной `@TaveloriBot` остаётся точкой выпуска. CloudStorage этих ботов разделён; тестовые данные не переносятся в основной автоматически.

Локальный dev-сервер Lexi открывается через HTTPS-туннель, адрес которого указывается в настройке Main Mini App dev-бота. Обычный браузер используется для быстрой отладки UI, настоящий Telegram — для CloudStorage и нативных возможностей. Смена адреса туннеля меняет origin локальной базы; для длительной разработки предпочтителен постоянный dev-адрес. В Vite разрешается конкретный hostname туннеля. Отдельный процесс обработки сообщений бота в текущем объёме не требуется.
