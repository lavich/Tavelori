# Отчёты о сбоях без сервера

## Контекст

Приложение — статический сайт на GitHub Pages и Mini App в Telegram; сервера, аккаунтов и логов нет (см. proposal.md — Why). Сейчас критические отказы глушатся: `main.tsx` пишет в консоль отказ открытия базы, регистрации service worker и подключения синхронизации, а границы ошибок в дереве React нет — любое исключение в рендере даёт белый экран. Стартовый JavaScript прекешируется PWA, поэтому его вес важен. Спецификация `local-first-app` обещает работу без аккаунта и хранение всего на устройстве; #11 требует явно описывать любой канал, по которому данные покидают устройство.

## Цели и не‑цели

**Цели:** узнавать о сбоях у пользователей без сервера; не отправлять ничего из учебных данных и данных запуска Telegram; читаемые стеки; никакого влияния на первый рендер; работа в частом офлайне.

**Не‑цели:** трассировка производительности, записи сессий, аналитика использования, обратная связь от пользователя (#11), собственный приёмник отчётов.

## Решения

### Sentry на бесплатном плане, а не свой приёмник

Бесплатный план Developer даёт 5 000 ошибок в месяц, релизы, группировку и загрузку карт кода — для одного пользователя этого хватает с запасом; при исчерпании лишнее просто отбрасывается без доплаты. Альтернативы: GlitchTip и Bugsink принимают тот же протокол и отличаются только адресом приёма, так что решение обратимо заменой одной переменной сборки. Собственный приёмник (Cloudflare Worker, пересылающий в бота Telegram) отклонён: он не даёт ни группировки, ни релизов, ни карт кода, а сообщения без стека мало чем помогут.

### Адрес приёма задаётся при сборке и включает весь механизм

Адрес приёма приходит переменной окружения сборки (`VITE_SENTRY_DSN`) из переменных репозитория GitHub и попадает в публичный бандл — это ожидаемо для браузерных SDK. Без переменной модуль отчётов не импортируется вовсе: разработка, unit‑ и e2e‑тесты никогда не делают запросов к сервису и не тянут чанк SDK.

### Ленивая загрузка с буфером ранних ошибок

SDK весит десятки килобайт, поэтому он загружается отдельным чанком после первого рендера, а не в стартовом модуле. Плата за это — ошибки запуска случаются раньше, чем SDK готов. Решение: точка входа сразу ставит крошечные обработчики `error` и `unhandledrejection`, складывает до десяти ранних событий в память и передаёт их в SDK после инициализации. Синхронная загрузка отклонена ради стартового веса; потеря ранних ошибок отклонена, потому что именно отказы запуска нам интереснее всего.

Чанк SDK попадает в precache PWA вместе с остальным JavaScript: офлайн‑запуск не должен отличаться от онлайн‑запуска ни поведением, ни набором ошибок.

### Офлайн‑транспорт

Приложение часто открывают без сети. Используется офлайн‑транспорт SDK, который откладывает недоставленные события в отдельное хранилище IndexedDB и отправляет при следующем запуске с сетью. Это отдельная база, а не таблица приложения: она не попадает в полную копию и не участвует в миграциях. Факт такого хранения описывается на экране «Копия данных».

### Очистка как чистые функции

Границы данных из спецификации реализуются двумя чистыми функциями — очистка события и фильтр хлебных крошек — которые подключаются в `beforeSend` и `beforeBreadcrumb` и покрываются unit‑тестами отдельно от SDK. Правила: `sendDefaultPii` выключен (SDK не передаёт IP и пользователя); адреса режутся до пути; поле пользователя удаляется; дополнительные поля проходят только из разрешённого списка (категория отказа, идентификатор и версия пакета); крошки консоли и кликов по DOM отбрасываются, остаются навигация (только путь), запросы к собственному контенту и события жизненного цикла Mini App. Интеграции трассировки и записи сессий не подключаются — и ради квоты, и ради границ данных.

Сообщения ошибок, которые формирует само приложение, проверяются: в проекте они уже короткие и технические («image», «audio», «Не удалось открыть локальную базу»), но задача включает аудит мест `new Error(...)` и `toast.error(...)`, чтобы ни одно не подставляло слово или ответ пользователя.

### Метки среды и крошки жизненного цикла Telegram

Каждому событию ставятся метки `env` (веб или Telegram), `tg.version`, `tg.platform` из bridge, `app.version` и `app.build`. События `activated`, `deactivated`, `viewportChanged` и `visibilitychange` пишутся крошками с высотами области просмотра — это ровно тот контекст, которого не хватает для #2. `initData`, идентификатор и имя пользователя не читаются модулем отчётов вообще.

### Граница ошибок и экран сбоя

В корне дерева React (внутри роутера, снаружи экранов) ставится классовая граница ошибок. Её запасной экран показывает объяснение, «Перезапустить» (перезагрузка страницы) и «Скопировать диагностику» — версию, среду, время и идентификатор отчёта. Граница ничего не пишет в базу и не трогает сессию: активное занятие уже лежит в IndexedDB, и после перезапуска «Сегодня» предлагает продолжить его штатно. Ошибки в обработчиках событий граница по природе не ловит — их закрывает глобальный обработчик.

Отказ открытия базы происходит до дерева React и обрабатывается отдельно в точке входа: отчёт категории «хранилище» плюс понятное сообщение в корневом элементе вместо пустой страницы.

### Явные отчёты через одну функцию

Модуль отчётов экспортирует `reportError(error, {category, extra})`. Её вызывают четыре места из спецификации: открытие базы, установка пакета, синхронизация, регистрация service worker. Без адреса приёма функция — пустая операция, поэтому вызовы безопасны в тестах.

### Настройка с включением по умолчанию

В `Settings` добавляется `errorReports:boolean`, по умолчанию `true`; `fillSettings` уже подставляет значения по умолчанию для старых записей, так что миграция базы не нужна. Модуль отчётов читает настройку после открытия базы и инициализируется только при включённой; выключение вызывает `close()` у SDK и очищает офлайн‑очередь. Включение по умолчанию выбрано сознательно: приложение личное, владелец — его единственный пользователь, и без отчётов канал не имел бы смысла; прозрачность обеспечивается описанием на экране «Копия данных» и переключателем в «Настройках». Если базу открыть не удалось и настройку прочитать нельзя, отчёт об этом отказе отправляется по умолчанию — это единственный случай, когда настройка не проверяется, и он назван в описании канала.

### Карты кода: скрытые и загружаемые из CI

`build.sourcemap:'hidden'` даёт карты без ссылок на них из бандла. Плагин Sentry для Vite загружает их при наличии `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` и `SENTRY_PROJECT` из секретов и удаляет `*.map` из `dist` после загрузки; без токена плагин не подключается, и сборка в проверках pull request проходит как раньше. Имя релиза — версия из `package.json` плюс короткий идентификатор коммита из `GITHUB_SHA`; то же значение попадает в метку `app.build`.

## Риски и компромиссы

- [Белый экран из #2 может не бросать исключение вовсе] → крошки жизненного цикла и меток среды всё равно попадут в следующий любой отчёт; кнопка ручного сообщения появится в #11 и переиспользует этот канал.
- [Блокировщики рекламы режут запросы к sentry.io в обычном браузере] → принимается; внутри WebView Telegram блокировщиков почти нет, а собственный туннель потребовал бы сервера.
- [Утечка учебных данных через сообщение ошибки или крошку] → чистые функции очистки с тестами, разрешённый список дополнительных полей, отключённые крошки консоли и кликов, аудит сообщений ошибок в задачах.
- [Исчерпание квоты 5 000 в месяц из‑за цикла ошибок] → `sampleRate` 1.0 только для ошибок, без трассировки; SDK сам объединяет повторы; при исчерпании события отбрасываются без доплаты.
- [Рост стартового бандла] → SDK в отдельном чанке после рендера; в проверке фиксируется, что стартовый чанк не вырос.
- [Офлайн‑очередь как ещё одно хранилище на устройстве] → отдельная база SDK, очищается при выключении настройки, описана на экране данных.
- [Отчёты у пользователя, который не знал о канале] → включение по умолчанию уравновешено видимым описанием и переключателем; приложение личное.

## Открытые вопросы

- Регион организации Sentry (EU или US) выбирается при регистрации и влияет только на адрес приёма; спецификация и задачи от него не зависят.
